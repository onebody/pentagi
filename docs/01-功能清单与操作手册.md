# PentAGI 功能清单与操作手册

本文面向使用者与运维/二开人员，聚焦系统“做什么、怎么用”。部署与运维细节见 [02-部署与运维文档.md](02-部署与运维文档.md)。

## 1. 系统定位与核心能力

PentAGI 是一套自托管的“AI 驱动渗透测试/安全研究编排平台”。核心能力可以概括为：

- 以“Flow”为单位组织一次完整的安全测试/研究任务（目标、上下文、执行过程、产物、报告）。
- 通过多 Agent/多工具编排（终端、浏览器、搜索、向量库、知识图谱等）推动任务推进。
- 所有命令执行与工具运行以 Docker 沙箱方式完成，隔离宿主环境。
- 通过 Web UI / REST / GraphQL 统一管理：Flow、模板、Provider、提示词、日志、截图、API Token。

## 2. 技术架构与模块地图（概览）

### 2.1 服务形态

- 前端：React + TypeScript + Vite + Apollo Client（SPA）
- 后端：Go（Gin REST + gqlgen GraphQL/WS），PostgreSQL + pgvector
- 可选组件：Langfuse（LLM 可观测）、Observability（Grafana/OTel/Jaeger/Loki/VM/ClickHouse）、Graphiti + Neo4j（知识图谱）
- 隔离执行：后端通过 Docker client 管理任务容器，在容器中运行安全工具/终端等

### 2.2 关键入口与主链路

- 后端启动入口：[main.go](../backend/cmd/pentagi/main.go)
- HTTP/GraphQL 路由聚合：[router.go](../backend/pkg/server/router.go)
- GraphQL Server（含 WS subscriptions）：[graphql.go](../backend/pkg/server/services/graphql.go)
- 核心业务编排（Flow/Task 驱动）：[flow.go](../backend/pkg/controller/flow.go)
- Provider 汇聚与配置加载：[providers.go](../backend/pkg/providers/providers.go)

系统关键数据流（简化）：

1) 用户在 UI 创建/进入 Flow → 2) 后端创建 FlowWorker 并加载 Provider 与工具执行器 → 3) 用户输入触发 Task/子任务执行 → 4) 执行过程中写入日志/截图/产物并通过 subscriptions 推送 UI → 5) 最终输出报告与可追溯记录。

## 3. 业务概念与数据对象

PentAGI 的核心对象可按“组织/权限、编排执行、产物与审计”三类理解：

### 3.1 组织与权限

- User：用户（本地账号或 OAuth）
- Role/Privilege：角色与权限点（用于细粒度控制各资源的 view/admin/download 等能力）
- Session：Web 登录会话（cookie）
- API Token：面向自动化的 Bearer Token（REST/GraphQL 调用）

### 3.2 编排执行

- Flow：一次测试/研究会话（类似“项目/工单”），绑定目标、模型/Provider、语言、状态等
- Task：Flow 内的阶段性任务（规划、扫描、验证、报告等）
- SubTask：Task 内更细粒度的步骤/行动（包含工具调用与产物）
- Container：执行环境容器（Flow 的 primary container 等）
- Provider：LLM/Embedding Provider 配置（OpenAI/Anthropic/Gemini/Bedrock/Ollama/Custom 等）

### 3.3 产物与审计追溯

- Logs：各类执行/消息/工具/搜索/向量库日志（用于审计与复盘）
- Screenshot：由 scraper/浏览器产生的截图文件及其元数据
- Prompt/Template：提示词与 Flow 模板（用于规范化流程、复用最佳实践）
- Analytics/Observability：可选的指标、链路追踪与 LLM 观测

## 4. 功能清单（面向用户）

### 4.1 Web UI（主要入口）

前端路由入口可在 [app.tsx](../frontend/src/app.tsx) 查看。主要功能区：

- 登录与身份认证
  - 本地账号登录（默认管理员账号见部署文档）
  - OAuth 登录（GitHub/Google，需配置）
- Dashboard
  - 系统概览、近期 Flow、运行状态等（以实际页面为准）
- Flows
  - Flow 列表/筛选/查看
  - 新建 Flow：选择模型 Provider、语言、模板等
  - Flow 详情：聊天/指令输入、实时日志、截图、任务图谱、产物查看
  - Flow 报告：输出与下载（前端含 `flows/:flowId/report` 路由）
- Templates
  - 管理/复用 Flow 模板
- Settings
  - Providers：管理 LLM Provider 与相关参数
  - Prompts：管理提示词
  - API Tokens：创建/吊销 Token（用于自动化调用）

### 4.2 API 能力（自动化/集成）

后端统一基路径：`/api/v1`（见 [router.go](../backend/pkg/server/router.go#L39-L75)）。

- REST：面向管理与数据查询（flows/tasks/subtasks/logs/screenshots/prompts/providers/users/roles/tokens 等）
- GraphQL：`/api/v1/graphql`（支持 WebSocket subscriptions）
- Swagger：`/api/v1/swagger/*`（默认公开，建议生产环境按需关闭）
- GraphQL Playground：`/api/v1/graphql/playground`（默认公开，建议生产环境按需关闭）

认证方式：

- Web UI：cookie session（登录后浏览器自动携带）
- 自动化：`Authorization: Bearer <token>`（API Token）

## 5. 操作手册（常见场景）

### 5.1 首次登录与安全基线

1) 打开 Web UI（默认 https://localhost:8443）
2) 使用默认管理员账号登录（默认值见 [README](../README.md#L763-L763)，生产环境必须修改）
3) 立即修改以下安全配置（至少）：
   - `COOKIE_SIGNING_SALT`（必须改为高熵随机值）
   - `PUBLIC_URL`、`CORS_ORIGINS`（按实际域名/IP 收敛）
   - 如对外提供服务，配置正式 TLS 证书（而非自签）

### 5.2 配置 LLM Provider（必选）

PentAGI 至少需要一个可用的 LLM Provider 才能驱动 Agent 工作。常见路径：

- Settings → Providers → 新建/编辑 provider
- 或通过环境变量配置（OpenAI/Anthropic/Gemini/Bedrock/Ollama/LLM_SERVER_* 等）

配置项和行为细节参考：
- 后端配置总览：[config.md](../backend/docs/config.md)
- Provider 控制器与默认 provider 装配：[providers.go](../backend/pkg/providers/providers.go)

### 5.3 新建并运行一次 Flow（推荐流程）

1) Flows → New Flow
2) 选择/填写：
   - 目标描述（建议包含：资产范围、允许测试的域名/IP、授权边界）
   - 模型与 Provider（建议与任务强度匹配）
   - 模板（可选：选择团队最佳实践模板）
3) 在 Flow 页面输入任务指令（建议结构化）：
   - 目标与范围
   - 禁止动作（如禁止破坏性 payload、禁止外联等）
   - 输出要求（报告格式、严重等级标准）
4) 观察执行过程：
   - 实时日志（工具调用、终端输出、搜索结果）
   - 截图（web 证据）
   - Task/SubTask 图谱（复盘路径）
5) 生成/查看报告（Flow Report 页面）

### 5.4 通过 API Token 做自动化调用（示例流程）

1) Settings → API Tokens → 创建 Token（仅授予必要权限）
2) 使用 Bearer Token 访问 REST/GraphQL
3) 建议实践：
   - Token 定期轮换与吊销
   - 给不同自动化系统使用不同 Token，便于审计与最小权限

### 5.5 常见排障

- 无法启动/报数据库错误：检查 `DATABASE_URL`、pgvector 容器健康状态、以及迁移是否成功（启动时自动跑 goose migrations）。
- UI 空白/接口报 CORS：检查 `PUBLIC_URL` 与 `CORS_ORIGINS` 是否一致、是否包含实际访问域名/端口。
- 无法执行工具/容器创建失败：检查 Docker daemon 权限、`/var/run/docker.sock` 挂载、以及宿主资源限制。
- OAuth 登录失败：检查回调地址是否与 `PUBLIC_URL` 对齐，确保 provider 的 client id/secret 已配置。
